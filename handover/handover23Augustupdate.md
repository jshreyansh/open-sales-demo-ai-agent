## Part 1 — How it started (2026-08-05, day one)

The project began with a planning document (`globalplan.md`, still at the repo root) that explicitly critiqued and simplified an earlier, more over-engineered original plan — it's worth reading not for nostalgia but because several of its reasoned-through decisions (why not browser automation, why a UI Registry instead of DOM manipulation, why session state has to be externalized) are still exactly how the system works today.

Then, in a single day, the project went from an empty scaffold to a working, voice-driven, deployed-nowhere-yet product demo:

- **Morning:** a deliberately minimal Phase 0 — one hardcoded page, a handful of hand-written components, a chat panel, a backend that ran one hardcoded script. The explicit goal was to prove the core mechanic (agent narrates, agent drives the UI) before building any abstraction on top of it.
- **Midday:** that got replaced with the real architecture that's still in use today — a UI Registry (pages → components → actions) that the frontend populates by self-registration and the backend validates every agent decision against, so the LLM can never hallucinate a page or action that doesn't exist. Real product pages (Dashboard, Analytics, Content Studio, Brand Kit) were built the same day, with design tokens and layout taken by directly inspecting the actual reference product's computed styles and DOM — not screenshots, not guessing. **This "match the real thing, verified by inspection, not eyeballing" discipline shows up constantly for the rest of the project's life.**
- **Also midday:** Meeting Mode shipped — a Google-Meet-style wrapper around the same product, chosen by a URL parameter, so the same demo could be framed either as "here's the product" or "you're in a live meeting about the product." This split is still exactly how the two modes work today.
- **Afternoon:** the backend was migrated from its original Node/TypeScript scaffold to Python/FastAPI — a deliberate decision made *ahead of* adding voice, specifically because Pipecat (the voice framework chosen) is Python-core, and running everything in one language avoided needing a second bridge service. This is the first of three genuine architectural pivots in the project's history (see Part 4).
- **Evening:** voice went in. Not smoothly — a real four-bug debugging chain the same night: VAD silently never actually wired up (a config field that didn't exist in the installed pipecat version), text-to-speech never actually synthesizing (a missing frame-bracketing requirement), voice activity detection chopping one sentence into five separate transcriptions (a timing constant that needed tuning), and only then did voice get embedded into the real frontend as a working widget.
- **Late night:** three more real bugs found by actually testing the thing live — a "shared screen" overlay that was fully clickable and broke the screen-share illusion, a duplicate chat widget competing with the real one, and — this is worth remembering as a category of bug — replies were being computed and transcribed correctly but genuinely never played out loud, because no audio-output component existed in the page at all.

**By the end of day one, the core loop worked: an AI agent, by voice or text, driving a real-feeling product demo.** Everything since has been building on, hardening, and eventually deeply re-engineering that same loop.

## Part 2 — The build sprint (2026-08-06 to 2026-08-08)

**Day 2** added DeepSeek as a second LLM provider (with its own real gotcha — its "thinking mode" silently rejects forced tool-use unless explicitly disabled, which became a recurring lesson any time a new LLM call was added later in the project) and fixed a real conversational bug where describing a business problem got a generic "let me show you" instead of actual reasoning — traced to the product's core differentiator (MLR-readiness — regulatory-compliant content generation) simply not being described anywhere the model could read it. The rest of day 2 was a pixel-matching sprint against the real reference product: sidebar, a critical voice-specific regression (API keys were being loaded *after* an import that reads them at module-load time, so voice silently ran on a keyword-matcher fallback with no LLM at all — the REST/chat path was unaffected, which is exactly what made it confusing to spot), the MLR Review/Approvals page, and the first two content-generation "studio" wizards — MagicReel (video) and MagicAvatar (a digital-twin presenter using a doctor's own voice and photo) — plus wiring both into the registry so the agent could actually drive them, not just open their landing pages.

**Day 3** shipped real barge-in (interrupting the agent mid-sentence, verified against 15 live interruptions with 2-3ms response time) and introduced `lead_in` — a short transition phrase spoken before an action fires ("let me pull that up") — after two earlier approaches to the same problem had failed. This pattern is still core to how the agent feels responsive today. The persona was renamed from an early placeholder to "Rachel" this day (it would change again later). The first attempt at a real production deployment also happened this day, surfacing a WebRTC/ALB networking problem that would not fully resolve until day 4.

**Day 4** is the second of the project's three genuine architectural pivots: the WebRTC problem turned out to be structural, not fixable with configuration — the production box's network setup (AWS ALB, private subnet) simply cannot carry WebRTC's raw UDP media, full stop. The entire voice transport was switched to WebSocket instead — described in the commit itself as "a swap at the two transport endpoints, not a pipeline rewrite," since VAD/STT/the agent/TTS in between don't care what carried the audio in. This is still the transport in use today. The same day: the first real auto-deploy pipeline (a self-hosted GitHub Actions runner installed directly on the box, because the private subnet has no route in for a GitHub-hosted one — this pattern is also unchanged today), a single-call concurrency lock, per-tab session identity, idle-timeout auto-hangup, and the persona's second and final rename — **Rachel became Fiona**, the name still in use.

**In three days, this project went from an empty repository to a real, voice-driven, deployed AI sales demo.**

## Part 3 — Maturing the product (2026-08-10 to 2026-08-18)

This stretch was slower-paced (1-4 commits most days) but structurally significant:

- **Aug 10:** a broad turn-taking redesign pass (hand-raise as a non-interrupting way to signal wanting to speak, MEDDIC-based sales qualification prompting, per-persona timezone/location grounding), plus real URL routing replacing the old `?mode=` query parameter, a visitor email gate, and a durable SQLite log shared by both backend processes.
- **Aug 11:** LLM replies started streaming directly into text-to-speech instead of waiting for a full response before speaking — a genuine latency win, and the direct ancestor of the much deeper streaming/turn-ordering work done in the final week (see Part 4). A turn-lock fix this same day is also the earliest ancestor of what would become, ten days later, a much more serious "two buffers answering out of order" investigation.
- **Aug 12:** a real client requirement landed — **Dushyant Sapre required the agent to actively steer every call toward five specific pieces of information** (what problem brought them here, current solution, daily users, past attempts, and an explicit ask to connect with a human rep). This shipped the same day as an AI-generated call-summary system and an admin dashboard to review them. Also this day: the first scripted 9-step platform walkthrough — and a real architectural lesson, documented in the commit itself, that would echo through the rest of the project: **state that's coarser than the actions it represents forces the model to guess its own position instead of just reading it off** — fixed by making the walkthrough's state one index per atomic action instead of a handful of steps each hiding several actions.
- **Aug 13-14:** a run of fixes driven by real colleague test calls — interruptions being silently dropped because a flag reset before a delayed transcript arrived, a farewell-repeat bug, broadening what counts as "the prospect wants to leave," auto-continue talking over an already-speaking visitor, and — worth flagging specifically — a bug where stale, backlogged replies could replay out of order instead of just answering the latest thing said. **This is the same category of bug that would be root-caused far more rigorously, with full millisecond-level evidence, on 2026-08-22** — it was seen and patched here first, in a narrower form, eight days earlier.
- **Aug 17-18:** the three separate hand-rolled highlight/cursor systems across different pages got unified into one shared mechanism, with a script added specifically to catch drift between what the frontend registers and what the backend's registry manifest expects.

## Part 4 — The turn-taking intensive (2026-08-20 to 2026-08-23)

This is the period covered in full detail by `backend/handover/handover23Augustupdatebackend.md` and `frontend/handover/handover23Augustupdatefrontend.md` — read those for the complete account. The short version, for the whole-project narrative:

This stretch opened with a rebrand (the product had been ContentIQ-branded; it became properly SwishX-branded here) and a landing-page redesign making the live demo itself the front door instead of generic marketing copy. Then, driven entirely by a sequence of real test calls — the founder's own calls, a colleague's keyboard/headphone test, and increasingly deliberate stress tests — the project went through its most intensive period of turn-taking engineering yet:

- A real telemetry system was built from nothing, because before it, the only timing signal available in production logs measured how long a whole reply took to *finish*, not how long it took to *start* — the wrong number to optimize.
- **The third genuine architectural pivot of the project**: after a bug where the agent silently restarted its entire platform walkthrough right after a prospect said goodbye — because a contradiction-detection guard was reading the assistant's own farewell language as permission to act — the fix was elevated from a one-off patch into a standing principle, explicitly discussed and agreed with the founder's engineering collaborator before implementing: **state must come from user intent, never be inferred from the assistant's own words.** A follow-up repo-wide sweep, requested specifically to check for the same bug class elsewhere rather than treating it as one-off, found two more instances of a closely related problem and fixed them the same way.
- A critical production crash (every single real turn throwing an error, masked for hours by a watchdog's own defensive exception handling) was found and fixed the same day it was introduced.
- Two more real turn-taking bugs were root-caused with genuine forensic rigor against real call transcripts and raw logs — one about two independent buffers answering out of order, one about the wait-before-answering logic not distinguishing a confidently-finished thought from an uncertain one — both fixed using the same discipline: reconstruct exactly what happened from evidence first, propose a fix, verify against both a stress-test harness and a live re-test call before calling it done. The second of those two fixes was explicitly researched against how OpenAI's and LiveKit's real production voice systems handle the same problem before being designed, rather than guessed from scratch.
- The most recent fix (early hours of 2026-08-23) addressed a subtler problem: even when timing and buffer-ordering were correct, a reply could still feel disconnected from what the agent itself had just said. That fix was verified the same night against the single hardest real-world stress test the project has seen — a 51-minute call where the vast majority of turns went through a forced/uncertain release path — and held up with no repeat of the disconnected-reply pattern anywhere in that call.

That same 51-minute call is also where the founder used the agent as a live brainstorming partner for its own product roadmap — asking it directly, repeatedly, for feature ideas that would help it close deals, while also giving it direct, specific, repeated feedback on its own turn-taking behavior in real time. The full transcript and synthesis of that call live in `backend/artTellsArtistTheNeed.md` — genuinely worth reading in full if you want to understand not just what this product does, but how the founder thinks about where it should go next.

## Key architectural decisions and pivots (the ones worth knowing, not relitigating)

1. **Node/TypeScript → Python/FastAPI, day one**, ahead of voice, to avoid a cross-language bridge to Pipecat.
2. **WebRTC → WebSocket, day four**, forced by the production box's ALB not being able to carry UDP — not a preference, a hard networking constraint.
3. **Walkthrough state granularity fixed from coarse steps to one-index-per-action, day eight (Aug 12)** — the first time a bug was fixed by changing what the state itself represented, rather than patching around it.
4. **Two-repo, no shared code, enforced by a registry contract and a drift-checking script** — held since day one.
5. **State must come from explicit user intent, never inferred from the assistant's own words** — established 2026-08-21 after a real production bug, explicitly agreed as a principle (not just a patch) with the founder's engineering collaborator before implementing.
6. **A deterministic backstop that exists to catch a genuine model miss must check whether the model already acted, not just whether a state field is empty** — an empty field is also true when the model considered the situation and explicitly chose something else.
7. **Prefer a continuous confidence signal over a discrete step-count or flat timer whenever one is actually available** — established 2026-08-22, after discovering the turn-detection model already computed exactly such a signal internally and it was being discarded.

## How this has been tested

There is no formal automated test suite committed to the repository as of this writing — the tests that exist (an adversarial turn-taking stress harness with a dozen scenarios, plus targeted regression tests for each specific bug found) live in session scratch space, not in git. What *has* been consistent, and matters more than any specific test file, is the discipline: **every non-trivial fix in this project's history, especially in the last week, traces back to a real test call — never a hypothetical.** The pattern, repeated dozens of times: something feels wrong on a real call → reconstruct exactly what happened from raw logs and transcripts, not assumption → root-cause the actual mechanism → fix it → write a test that would have caught it → re-verify against a fresh live call before calling it done. Several real near-misses in the project's history (a masked crash, a harness that silently tested the wrong thing twice) happened specifically in the narrow cases where a step in that discipline got skipped — worth treating as load-bearing, not optional process.

## How this has been shown to people

Real test calls, escalating in formality and rigor over the project's life: early colleague calls that surfaced walkthrough and interruption bugs (Aug 13-14), a specific client requirement (Dushyant Sapre's five-question qualification KPI, Aug 12) that shaped a real feature rather than a hypothetical one, a keyboard/headphone-specific test that found real audio-quality issues (Aug 21), and — the most recent and most extensive — the founder's own direct, repeated, deliberately adversarial testing, culminating in the 51-minute call (Aug 22-23, `a0ef497f`) that was run explicitly as a combined stress-test-and-brainstorm session, treating the agent as something worth asking for its own opinion on how it should improve.
